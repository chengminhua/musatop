# v0.1.1：Toolkit 与功率上限 N/A 定位记录

日期：2026-10-08。以下仅保留软件版本与必要证据，不包含机器地址、账号、GPU UUID、业务进程或原始日志。

## Toolkit：安装路径漏检，已修复

问题节点安装了 `/usr/local/musa-4.3.2`，但没有 `/usr/local/musa` 软链接，且 `mcc` 未进入 PATH。其 `version.json` 中 `musa_toolkits.version` 为 `4.3.2`。v0.1.0 只读默认软链接下的文件，因此错误显示未知。

v0.1.1 增加显式环境变量、PATH 编译器真实位置和唯一版本目录的发现逻辑。以安装元数据为依据；明确选择有错误时报告错误，不悄悄切换到另一个版本；多个未选择的安装也不会猜测最新版本。不需要修改系统软链接或环境配置。

## 功率上限：GMI 未提供有效数值

| 只读对照 | 问题节点 A | 对照节点 B |
| --- | --- | --- |
| GPU / 数量 / 显存 | X10000 / 8 / 每卡 80 GiB | X10000 / 8 / 每卡 80 GiB |
| 驱动 | 3.3.7-server | 3.3.8-server |
| GMI | 2.3.3 | 2.3.3 |
| 系统 MTML 库 | 2.2.0-linux | 2.3.5-linux |
| MTBios | 4.3.45 | 4.3.45 |
| GMI 当前 / 默认功率上限 | N/A / N/A | 950 W / 950 W |
| 实时功耗 | 可读 | 可读 |

1. **原始 GMI 已经是 N/A**。musatop 的 JSON 解析没有丢失该数值；实时功耗和上限是不同查询。
2. **交叉运行两台现有 GMI 二进制**：两份程序在 A 上均返回 N/A，在 B 上均返回 950 W，排除这两份 GMI 程序差异。程序使用内嵌查询实现，动态加载跟踪未发现加载系统 `libmtml.so`，不能仅凭系统 MTML 版本判断原因。
3. **仅调用旧 MTML 的只读 getter**：A 上八卡当前/默认上限的 getter 均返回成功，但输出为 0 mW；实时功耗正常。这个零值没有提供有效上限，不能当成 0 W。没有向应用加入私有 MTML 接口或填入 B 的 950 W。
4. **驱动模块静态对照发现相关门控差异**。两机正在加载的模块 `srcversion` 与检查的磁盘模块一致，分析对象均为 `mtgpu.ko`：

| 路径 | 3.3.7-server | 3.3.8-server |
| --- | --- | --- |
| `pinghu1_get_power_limit_range` | 固件 TBP 配置项 `usrCtrl == 0` 时返回 6，不允许继续（`0x1fc331–0x1fc3c7`） | 读取并保存该标志，删除零值拒绝（`0x1fe311–0x1fe319`） |
| `mtgpu_probe` 初始化 | 查询范围失败后释放并清空 `user_ctrl_pl`（`0x79761–0x79766`） | 失败时只清零 `enable`，保留结构（`0x793cb`） |
| `mkis_get_power_limit` | 结构为空或 `enable == 0` 时全部返回状态 2（`0x22fa9c–0x22faac`） | 结构存在但 `enable == 0` 时仍允许类型 2、3 查询（`0x231b43–0x231b4f`） |

随驱动交付的 `inc/mtgpu/mtgpu_smc.h` 将 `usrCtrl` 定义为是否允许用户控制；它不是温度/功耗传感器状态。旧路径将上限读取也受限于可调节能力，新路径放宽了只读查询。两版头文件的最低 MTBios 条件都是 4.3.42，而现场均为 4.3.45，现有证据不支持因未达到这一版本门槛而失败；没有排除其他固件兼容问题。

**证据边界**：已经证明数值缺失在应用之外，也确认了与现象一致的驱动实现差异；没有读取运行态内核结构，未在同一节点更换驱动做 A/B 实验，因此不能断言现场具体命中“空指针”还是“enable 为零”分支。类型 2、3 的枚举名称没有足够依据；内核状态 2 也不等同于 MTML 错误码 2。上述地址仅适用于本次检查的模块构建。

## 应用修复与后续处理

v0.1.1 将不可用/零上限保持为 `null`，新增设备 `power_limit_reason`；文本、TUI 底部和帮助说明其含义。Toolkit 新增 `musa_version_source` 和 `musa_version_reason`。正常指标与采集保持可用，未知可选指标不导致整轮报错。

建议下一步在维护窗口验证厂商认可、包含相关查询修复的驱动；是否恢复数值，须以升级后 `mthreads-gmi -q --json` 的原始结果验收，目前未在节点 A 验证。对照节点的 3.3.8 提供了候选版本证据，并不代表已经验证所有 3.3.8 安装。此次没有升级驱动、重载模块、修改 GPU 功率参数或终止业务任务。
